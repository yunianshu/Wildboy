# WildBoy：功能驱动的 A 设计任务书

## 最新要求

2026-11-18 用户纠正：不要参考 B 方案的设计，希望从项目功能角度设计。A「晨光绿白」仅作为视觉方向，不作为旧 B 布局的改色指令。本轮不修改已推送的生产代码。

## 依据优先级

1. 当前 router / app.json、页面逻辑、类型、后端校验与接口。
2. PRODUCT.md 中仍符合代码的产品规则。
3. 用户在当前对话的明确要求：操作简单、活动与商品优惠分开、没有课程业务。

旧 design/画板、B 图片和过期范围文档不作为新布局来源。`docs/product-scope.md` 中“收费报名不支持”与当前实现不符，不沿用。

## 角色必须分清

- 未登录浏览者：浏览活动与装备，不取得报名人资料。
- 微信用户：本人联系人、参与人、报名/订单、地址、付款恢复与售后。
- 散客 / 会员 / 领队：决定服务端报价的业务身份，不自动获得管理权限。
- 管理员：活动生命周期、名单与订单处理、商品履约、会员定价、用户授权、内容和配置；权限受真实服务端限制。

## 核心任务顺序

1. 活动：找到合适活动 → 确认时间地点与剩余名额 → 参与人及协议 → 服务端报价 → 免费确认或支付 → 查询结果/报名与通知。
2. 商城：筛选商品 → 查看规格/现价库存 → 地址数量与会员报价 → 创建订单/支付 → 查询、取消或售后。
3. 活动运营：准备草稿/模板 → 核对发布 → 跟进报名或待支付 → 名单/变更通知 → 取消与退款恢复。
4. 交易处理：按订单真实状态提供核对、退款、实际发货与上报；未知结果不冒充完成。
5. 会员定价：在同一等级编辑中并列展示“活动”和“商品”，每项直接选择折扣/固定价/减免；活动再明确全部参与人或最多一人，不设计多步向导。
6. 管理授权与身份资料：来源/角色/脱敏状态清楚，揭示和授权为显式确认，不与优惠身份合并。

## 页面组织原则

- Web：持续可见的任务导航，表格用于跨条目比较，订单操作就近，复杂编辑使用明确分区和保存条，不编造统计或新增服务。
- 小程序：一次完成一个任务，触控主动作固定或就近可达，风险/结果/恢复动作与数据同屏。既有四 Tab 和用户首页约束继续适用。
- 新稿覆盖真实字段、主次动作、权限、空/加载/失败/冲突/未知支付结果，不用静态成功掩盖真实状态。
- 视觉只沿用 A：白底、叶绿 #247A52、浅绿 #EAF4E7、深绿文字 #20372C；真实品牌与照片，无 B 导航或卡片复刻。

详细路由及字段以本轮 `functional-web-inventory.md`、`functional-mini-inventory.*` 的源码证据为准。
