# 用户管理、商品分类与双价专项（2026-10-31）

本批落实用户提出的用户资料与管理权限、商品分类、原价/现价，以及删除「我的」页多余入口。本文区分源码/本地测试、独立数据库测试与原生/手机验收。编写时根代理正在汇总运行库升级、最终全量构建和原生验收；下文不把旧预览包、模拟 wx 或前批截图当作新功能已经在手机通过。

## 用户身份与必要资料

- 微信登录只兑换一次性 code。本项目不依赖登录自动取得真实姓名、手机号，不要求头像或昵称授权；「活动联系人」由用户主动填写本人姓名和中国大陆手机号。
- `User` 的账号来源 `accountSource` 与权限 `role` 分开：来源为 `WECHAT / PASSWORD / DEMO / OTHER`；另有 `wechatVerified` 与角色版本 `version`。只有真实微信提供方成功登录链会设置微信验证标记，不能通过客户端传 role、昵称或头像获得该资格。
- 联系资料允许普通用户及已验证的微信管理员维护；密码管理员不填写活动联系人。本地演示普通用户的资料流程保留，但演示账号不能被授予管理员。
- 报名前由当前会话读取本人资料；缺少已完成资料时引导显式填写。只向空白或仍匹配旧本人资料的首位参与人回填姓名、手机号，用户自行编辑后不会被刷新覆盖，其他同行人不变。
- 多人报名继续分别添加、编辑和确认删除。姓名、手机号逐人必填；身份证号仅在活动 `identityRequired` 时显示、校验和发送，不需要时不发送隐藏旧值。历史报名保留提交时的参与人快照，不因联系人更新而改写。
- 协议正文可主动查看，不强制逐份打开。资料保存与报名默认不勾选，必须主动同意当前已发布版本；获取失败不放行，版本变化清除同意并提示重取。打开资料页协议返回只恢复同账号草稿，仍不自动同意。

对应原生入口为 `pages/profile/index` 与「我的 → 活动联系人」；`pages/register/index` 提供完善资料后的返回与首位回填。新页已移除与原生导航重复的大标题，说明和操作保留。

## 微信管理员授予与撤销

用户管理位于 `pages/admin-users/index`，Web 同样提供用户资料、脱敏报名历史及角色操作。列表支持搜索、资料状态、角色和账号来源筛选；管理展示默认采用服务端脱敏姓名/手机号。

| 契约 | 行为 |
| --- | --- |
| `GET /admin/users`、`GET /admin/users/{id}` | 返回真实账号来源、权限、角色版本、报名历史，以及 `canChangeRole / roleChangeBlockReason`。 |
| `PUT /admin/users/{id}/role` | 请求 `{role: USER\|ADMIN, version}`；用户须明确确认目标与权限影响，响应再核对目标 ID、角色与新版本。 |
| 操作者 | 仅密码管理员或已验证微信管理员可写角色。演示/其他管理员对该功能只读，其余既有活动/商品管理不因此额外收紧。 |
| 目标 | 仅已验证微信账号可授予或撤销。禁止修改自身、把密码/演示/未验证账号作为目标，并保留最后管理员保护。 |
| 并发/拒绝 | 过时版本返回 `409 STALE_VERSION`，不能重复提交旧体，需重新读取。自改、不合资格目标或最后管理员保护也由服务端拒绝。 |
| 会话 | **授予与撤销均撤销目标所有会话。** 目标下次请求收到 401 后，由用户主动微信重登获取新角色；不伪造本地 role，也不自动替用户登录或同意。 |

授权改变的是同一微信账号的权限，不新建账号，不迁移或清除其联系人、报名与订单。再次微信登录允许接收服务端确认的、已验证微信账号 `ADMIN`；密码管理员登录仍走独立密码入口。`/auth/capabilities` 只控制该密码入口，已登录微信管理员按真实 `/me` 角色显示管理操作。

小程序对角色写入去重，显式区分「只读操作者」与真正身份/权限失效。收到真正 401/403 后清空用户列表、详情、搜索手机号等草稿，并同时失效列表/详情/角色请求世代，早先 200 响应不得重新填回私有记录。跨账号的参与人删除确认也不能改动新账号名单。

## 商品分类

分类是独立实体，不用商品名或前端假卡片充当分类。

| 接口 | 返回或请求 |
| --- | --- |
| `GET /shop/categories` | 公共数组 `{id,name,sortOrder,version}`。 |
| `GET /admin/shop/categories` | 同项加 `productCount`。 |
| `POST /admin/shop/categories` | `{name,sortOrder}`，成功返回服务端创建的分类。 |
| `PUT /admin/shop/categories/{id}` | `{name,sortOrder,version}`；不提供删除。 |
| `GET /shop/products?categoryId=...` | 仍返回商品数组，由服务端实际筛选；省略分类为全部。 |

现有商品迁入稳定分类 `uncategorized`，初始名「未分类」、排序 9999，可按版本改名/排序。分类名称 trim 后 1–40 字、不得有控制字符，忽略大小写唯一；重名为 `409 CATEGORY_NAME_EXISTS`，过时版本为 `409 STALE_VERSION`，无效商品分类为 `400 CATEGORY_NOT_FOUND`。

小程序在 `pages/admin-product/index` 商品编辑页内提供分类选择及可展开的创建/编辑管理，无独立分类路由。分类加载失败独立重试、不丢商品草稿；分类版本冲突保留草稿并要求重新读取。创建结果不确定时先读列表核对，未找到同名项需明确确认后才允许再创建。编辑别的管理分类不会顺手改商品归类，创建成功才采用权威新分类 ID。

商城分类条保留原生 `scroll-x`，复用活动页已验证的 track 几何：以选中项相对轨道的位置计算中心，用轨道宽度限制边界，不使用动画期间可能滞后的 `scrollOffset/scrollWidth` 或单向 `scroll-into-view`。保留重复选择、触摸、resize、离页及迟到查询保护，触控至少 44px，长名称截断并保留完整可访问名称。

公共目录缓存与在途请求按分类 ID 分桶，各 30 秒：切回复用本类结果；成功空列表也算已加载；过期后台刷新保持该类商品可点；失败保留该类上次结果并可重试。A→B→A 快切不会串结果或排队重复请求，卸载后迟到数据不能回填，新实例不复用旧缓存。分类元数据加载失败不影响「全部商品」。商品详情、结算和订单继续实时请求，不缓存私有会话/地址/订单。

## 原价、现价与首页范围

- `priceCents` 继续代表现价和成交价，`originalPriceCents` 为展示原价，均为整数分，范围 1–100000000。原价不得低于现价。
- 新 UI 明确填写商品分类及双价。旧客户端新建缺省分类为未分类、原价等于现价；编辑缺分类保留原值，缺原价按 `max(旧原价, 新现价)` 兼容。
- 商品卡、详情及首页真实装备数据只在有效原价高于现价时显示划线价；等价、缺失或异常原价不造折扣，不从 `priceLabel` 反推分值。
- 商城卡片名称最多两行；原价单独位于主价行上方，现价与库存继续同排、底部对齐。首页只在用户授权范围内增加真实商品原价字段及必要价格行/对齐，原有四商品上限、横幅、图片、透明原标识、导航和活动结构保留。
- 结算、支付和历史订单不使用展示原价重新计算，历史订单成交快照不变；`requestPayment` 成功回调仍不等于服务端已支付。
- 首页活动上限为六个真实已发布记录，不足不复制。源代码不是要求运行库必须凑足六个；下述 QA 清理后数量可能少于六个。

用户另明确要求删除「我的」页整块「继续探索 / 发现下一次出发」及其专用处理器；底部探索 Tab、其他活动入口、报名返回与全部普通业务保留。
